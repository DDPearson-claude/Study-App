## KQ1. What exactly does Dan see and do, step by step, in a current lesson in each mode, and how long is it?

### Takeaway
A course is a plan of 5-8 "ideas", each meant as "one five-minute lesson built around a bespoke interactive". A study-mode lesson walks five fixed stages (Predict, Play, Explain with analogy and "Put it into practice", Say it back, Check); a "Just teach me" (read-mode) lesson walks two (Read: the explanation; then Explore: the interactive with "What you're looking at" open, then the comparison, practice, sources and a recap). The repo records no measured lesson duration: the only time figures are the plan prompt's "five-minute" intent, the generation latencies, and the review's per-card seconds.

## KQ2. Which parts of the current flow are fixed, which could a pre-built course drop or change, and which are tied to how review makes cards?

### Takeaway
The lesson JSON, the validator, the fact-check, the kit and the lesson screen are all keyed to the same parts (predict, interactive with 1-2 controls and 0-3 outputs, explain, analogy, practice, say, 2-3 checks, sources, confidence). Review cards are made only from what Dan answered (each check he answered, keyed `iid_checkId`, and his say-it-back as a `recall` card keyed `iid_say`), so dropping checks or say-it-back drops review for that idea entirely (read mode already does exactly this); changing a check's question resets its schedule; the verifier is forbidden from touching anything cards or the interactive are keyed to.

### Cited Findings

**The generation pipeline (what is fixed by code, not by prompt wording)**
- Pipeline per lesson: claim the doc (`writing`), wait for research, write the lesson for the topic's mode with research, `known` ideas, `prior` (summaries of earlier lessons), `avoid` and `feedback`; a reply that still fails validation after one repair is rewritten once from scratch; stamp `lesson.mode`; keep only citations of checked sources; save `building`; then the fact-check and the interactive build run side by side; save `ready` once both are over — [docs/ARCHITECTURE.md:916-934](docs/ARCHITECTURE.md#L916). Tiers: intake and plan quick; build/repair complex; the rest default — [:794](docs/ARCHITECTURE.md#L794).
- One writer per lesson across devices: a 90 s db lease renewed every 45 s — [docs/ARCHITECTURE.md:1001-1011](docs/ARCHITECTURE.md#L1001). Prefetch: once a lesson is whole the next open idea is prepared in the background — [:1103-1114](docs/ARCHITECTURE.md#L1103).
- The write-lesson prompt's fixed frame "HOW DAN MEETS THIS LESSON (each part of your JSON appears on his screen, in this order)": "1. predict: before playing, he commits to a guess ... Committing first makes the answer stick."; "2. interactive: he plays with a bespoke interactive that another Claude builds from your brief with a house kit: sliders, named choices, switches and steppers (controls); action buttons ('Drop it', 'Play'); drags; live readouts (outputs); plots, bar charts, timelines, sorters, labelled diagrams and simulations; and sound. ### Inferences
- Parts a pre-built course could drop with no code change, by writing lessons in read mode: predict, say-it-back, checks, review cards, calibration warm-up, intake (an intake is only asked for a typed topic). Read mode is already a shipped, tested shape and NEXT.md's Saturday plan says to build the shelves in it ("mode 'read' unless he says otherwise").
- Parts the screen will not render unless the lesson JSON has them in the schema's shape: anything outside `predict / interactive / explain / analogy / practice / say / checks / sources / confidence / contested`. A Brilliant-style sequence of several small problems per lesson has no slot: a study lesson has exactly one predict, one interactive (1-2 controls), one say and 2-3 checks, enforced as hard counts by the validator and as fixed stages by `STAGES`.
- Review coupling: cards are made from `lesson.checks` and `lesson.say` and from Dan's first answers to them. Any new "problem" format that should feed review would need either to be expressed as one of the five card types (choice/order/estimate/target/recall) with a stable id, or a new card type in 41-cards.js plus `TYPES` in 60-today.js. Changing a check's wording after a card exists resets its FSRS state (`sameQuestion`); target cards die if the interactive is rebuilt.
- The verifier's frozen set shows which fields the system treats as load-bearing: predict question/options (answered), the interactive spec (built), check ids/types/answers (cards), sources (checked against pages). A pre-built lesson written offline would still be stored in this shape, so the same fields stay load-bearing once Dan has started it.

### Gaps
- The repo has no mechanism to store a lesson without going through `ensureLesson`'s validator and build; NEXT.md's plan to "save the topic and its lessons to the db as 'ready'" from a Claude Code session is a plan, not code ([docs/NEXT.md:51-55](docs/NEXT.md#L51)). Whether the lesson screen tolerates a hand-written doc that skips `verified`, `selftest` or `by` is not tested anywhere I found.

## KQ3. Which weaknesses did the evals and reviews find that a pre-built course, written with more time per lesson, could fix?

### Takeaway
The run-2 three-judge panel scored eight generated lessons 3.13/5 overall (predict 2.96, interactive 3.00, checks 3.17, explain 3.54, say-it-back 3.79, accuracy 3.63) and found seven causes shared across most lessons: the predict answers itself, checks test recall, interactives show only the effect, absolute claims that are false, the explanation skips the causal step, research too thin, and labels unreadable on a phone. Dan's own 7 Oct feedback adds two more: explanations too short to teach ("120 words is tiny") and the interactive arriving before the idea it assumes. The subject experts listed dozens of concrete accuracy errors that a slower, checked writing process could avoid.

## KQ4. What can the interactive kit do today, and what would a Brilliant-style "problem first, manipulate, then explain" lesson need from it that it lacks?

### Takeaway
The kit is a sandboxed, no-network page with one `K.model → K.update` pipeline, five control types (slider, named choice, toggle, stepper, button) plus drag, readouts, canvas plots, bars, animation, sound, SVG label placement and a strict self-test; the host can set controls, press buttons, read state, hide one readout (quiz mode) and check reachability. It has no text or number entry, no multi-step problem sequencing, no per-problem grading inside the frame, and the only graded interaction on an interactive is the single "target" check (reach a readout value by moving one control).

### Cited Findings
- What the model writes: "the BODY of one page: HTML, an optional `<style>`, then one inline `<script>` ending with `K.ready()`. It runs in a sandboxed iframe on Dan's phone (about 340 px wide, touch) and laptop ... No network or storage: no web addresses, `fetch`, `localStorage`, `alert` or `prompt`." — [app/kit/KIT.md:3-6](app/kit/KIT.md#L3). Body at most 150 KB (`MAX_BYTES`); the build prompt asks for under 40 KB — [app/src/js/32-sandbox.js:38](app/src/js/32-sandbox.js#L38), [app/src/js/33-interactive.js:228](app/src/js/33-interactive.js#L228).
- Sandbox: `sandbox="allow-scripts"` (never `allow-same-origin`), CSP `default-src 'none'; script-src 'unsafe-inline'; style-src 'unsafe-inline'; img-src data:; font-src data:; media-src data:; connect-src 'none'; form-action 'none'; base-uri 'none'`; a per-frame token signs every message; a frame that navigates away or stops answering the 2 s heartbeat is removed — [app/src/js/32-sandbox.js:41-42](app/src/js/32-sandbox.js#L41), [docs/ARCHITECTURE.md:636-665](docs/ARCHITECTURE.md#L636).

### Inferences
- What the kit can already do for a "problem first" lesson: pose a situation visually, let Dan manipulate it (slider, drag, choice, stepper, button), hide the answer until he moves, hide a readout while he is "answering" (quiz mode), and let the host grade a numeric outcome by reading `get()` (the target check does exactly this). A named `K.choice` plus host-read `change` messages could in principle serve as a multiple-choice answer on the picture, but there is no host code that does so today.
- What it lacks for a Brilliant-style lesson: (1) a way for Dan to type or enter a number or expression inside the frame (no inputs, and the kit's `.say`/readout echo rules assume numbers only come from the model); (2) a sequence of several problems in one frame with per-problem feedback and a "next" progression (the kit is one model, one state, one page; `K.stepper` walks steps of a drawing, not graded problems); (3) in-frame right/wrong feedback (checks are self-test assertions, not learner feedback; grading lives in the host's card renderer); (4) a host contract for anything but the single target check (`reach`/`quiz` cover one output of one control); (5) free-layout diagrams the learner builds (drag exists only as "move the thing to set a control's value").

### Gaps
- There is no exemplar or kit feature for a "multiple small problems" page, and nothing in docs/eval tested a puzzle-first interactive; whether Dan wants typed answers inside interactives is not recorded.

## KQ5. How are lessons stored, what are the size limits and platform constraints, and how would a course with many pre-built lessons fit (including the shelves mechanism)?

### Takeaway
A course is one `topics/{tid}` doc (the plan) plus one `topics/{tid}/lessons/{iid}` doc per idea (the lesson JSON, the built interactive HTML up to 150 KB, its self-test report and the fact-check record) plus `topics/{tid}/research/{key}` docs; Dan's progress, cards and dossier chapters are private docs keyed by tid. Each doc must stay under 256 KiB, so a course of many lessons is limited per lesson, not per course. The ready-made shelves are db docs `shelves/{sid}` (four shelves, 100 courses, all `tid: null`); the app shows "Not built yet" until a build session writes a course's `tid`, after which "Ready to browse" links to `#/t/<tid>`. The platform is plain JS in one artifact: no frameworks, no server, sandboxed iframes, no video, phone-first 360 px, Claude only through `sample`, research only through Parallel Search, pictures through the Hugging Face connector.
